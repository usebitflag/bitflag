# M12. Release acceptance

Status: draft for review, 6 October 2026. Follows [00-conventions](00-conventions.md). Expands M12 in the [implementation plan](../implementation-plan.md) and maps to the complete-product release gates in [operations and release](../../../bitflag/docs/operations-and-release.md) §8.

## 1. Goal and scope

Prove, with recorded evidence, that the complete product is safe to launch: every agreed screen works, is accessible and responsive, tenants are isolated, the system holds an agreed load, it can be restored from backup without breaking SDK ordering, it is monitored with named owners, and data is kept only as long as the policy says. M12 ends with a go/no-go decision by Shei.

**In scope**

- Mockup coverage audit: every artboard mapped to a Cypress spec or an explicit "not built" decision.
- Accessibility acceptance (WCAG 2.2 AA proposed), automated and manual.
- Responsive acceptance at fixed viewports with defined behavior per width.
- Security review: threat model, review checklist, headers and cookies, external penetration test, tenant-isolation test suite across every route, query, job, cache key and export.
- Dependency, secret and bundle scanning in CI for all four core repositories, plus SBOMs.
- Load test plan and runs against targets agreed under D08; failure-injection runs proving workload isolation.
- Backup and restore drill, including the delivery generation bump and cached SDK clients.
- Monitoring, alerting, synthetic canaries, on-call ownership, incident process.
- Runbooks for every scenario in operations §6, each rehearsed once.
- Data retention verification for every data class.
- The go/no-go checklist and its evidence pack.

**Out of scope**

- Building features. Defects found here are fixed in the owning module with a test; M12 tracks them.
- Choosing a hosting provider, monitoring vendor or penetration-test vendor (D08). M12 lists what must be decided and verifies whatever is chosen.
- Building or accepting the SDK clients, adapters, CLI, MCP, website and docs: those are [M13](M13-sdks-tools-and-sites.md), whose done criteria are the evidence for go/no-go gates 7 and 8.

## 3. Design

### 3.1 Data model

M12 adds no customer-facing tables.

**`retention_runs`** (system table, not tenant-owned; evidence for retention verification)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | ulid | |
| `job` | varchar(80) | For example `PruneTelemetry`, `PruneIntegrationRecords`, `PruneAuditVisibility` |
| `data_class` | varchar(40) | Domain model "Time, retention and data classification" class |
| `table_name` | varchar(64) | |
| `cutoff` | timestamp(6) | |
| `rows_deleted` | bigint | |
| `started_at`, `finished_at` | timestamp(6) | |
| `status` | enum(`succeeded`,`failed`) | |

Every prune job from M2 to M11 writes one row per table per run (M10 and M9 already reference it).

**`operational_events`** (system table): `kind` enum(`generation_bump`, `restore_completed`, `drill_started`, `drill_completed`), `details` json, `actor` (ops user name from the console command), `occurred_at`. Customer-visible effects are also written to each affected organization's audit with channel `system`.

`publication_pointers.generation` and generation-aware delivery come from M5, which owns `generation` and its command `bitflag:delivery:bump-generation`. M12 extends that command with `--all`, `--reason`, an interactive confirmation, audit and outbox (`BumpDeliveryGeneration`, below).

**Generation values must exceed anything clients have seen, even after repeated restores.** A restored database does not know the highest generation that was issued after its backup point, so "restored value + 1" can be lower than what clients already hold (restore a backup at generation 1 after clients reached 3, and +1 gives 2, which clients correctly reject). The bump therefore sets `generation = max(current + 1, unix_seconds(now))`. Ordinary environments start at 1, every bump jumps to the current wall-clock second or above, and each later restore happens later in time, so it always produces a higher value. `int unsigned` holds this until 2106 and stays inside JavaScript's safe integer range. Generations are opaque increasing integers in the protocol; clients only compare them.

**Recovery journal** (`App\Shared\Recovery`, external to the restorable database; storage chosen under D08, for example a versioned, write-once object-storage prefix or a separate small database with its own backups). An outbox consumer appends one line per security- or privacy-relevant change, with IDs, type and time only (no secrets, no subject keys): credential revoked, rotated, expired or scopes reduced; personal token revoked; organization or project membership removed or role lowered; invitation revoked; sessions revoked, password changed or reset, MFA disabled or reset; organization suspended; telemetry subject deletion (environment, key version and hash). Producers in M2, M3, M7 and M10 already emit outbox messages for these; M12 registers the consumer and adds any missing message. Its recovery point is the outbox lag (seconds), not the backup interval. Lines are retained for the longest backup retention plus 30 days.

### 3.2 Domain rules and state machines (acceptance criteria)

**Accessibility (proposed WCAG 2.2 level AA; see §6).**

| Area | Rule | How verified |
| --- | --- | --- |
| Automated | No axe-core violations of serious or critical impact on any page state visited by Cypress | `cypress-axe` via a `cy.checkA11yState()` helper called after each state in every spec; CI fails on violations |
| Components | Dialogs, menus, tabs, switches, comboboxes follow WAI-ARIA patterns | Vitest with `vitest-axe` per `components/ui` primitive; keyboard tests with Testing Library |
| Keyboard | Every flow in the coverage matrix completes with keyboard only; visible focus; focus returns to the trigger after dialogs; no traps (except one-time secret dialogs, which keep focus by design and remain escapable only after acknowledgment) | Manual pass, recorded per flow |
| Screen readers | Primary flows announced correctly; async results in a polite live region; toasts not duplicated | Manual pass with VoiceOver + Safari and NVDA + Firefox |
| Color and contrast | Text 4.5:1, large text and UI components 3:1 in both themes, status never by color alone | `tests/js/tokens-contrast.spec.ts` computes ratios for every token pair the components use (including the 55% muted text mix) |
| Reflow and zoom | Usable at 200% zoom and at 320 CSS px width without two-dimensional scrolling, except data tables and the rule editor, which scroll inside their container | Cypress viewport run plus manual zoom check |
| Charts | Every chart has a text summary and a data table alternative | Component tests (M10, M11) |
| Drag and drop | Rule and environment reordering have keyboard alternatives (move up/down buttons) | Cypress keyboard spec |
| Motion and time | `prefers-reduced-motion` respected; session expiry warns before signing out | Vitest, Cypress |

**Responsive.**

| Width | Expected behavior |
| --- | --- |
| 1440 and 1280 | Full layout as drawn (mockups are 1440 wide; frontend doc §7 calls out 1280) |
| 1024 | Full administration; sidebar collapses to icons; two-column panels stack where they would truncate |
| 768 | Read everything; review, approve, publish, roll back, emergency disable, revoke keys; editors usable with stacked panels |
| 390 | Read, review and approve, roll back and emergency disable, key revocation; complex editors (rule builder, segment editor, experiment setup) show "Best on a larger screen" but stay functional |

Global rules: no horizontal page scroll at any width (tables scroll inside their own container with a visible scroll affordance), dialogs become full screen below 640 px, the environment context (name and protection) stays visible in the sidebar environment picker, or in the top bar when the sidebar becomes a drawer below 1024 px, filter bars wrap.

**Security review checklist** (OWASP ASVS level 2 used as the checklist framework, proposal):

- Threat model per surface in `docs/security/threat-model.md`: portal, management API, SDK delivery and ingestion, outgoing webhooks and egress, inbound provider webhooks and OAuth, admin console, background workers, CI/CD and supply chain.
- Authentication and sessions (M2): lockout, MFA, recovery, session revocation, cookie flags `Secure`, `HttpOnly`, `SameSite=Lax`, host-only.
- Headers asserted by a Pest test on representative responses: CSP with nonces from Vite (no `unsafe-inline` scripts), `Strict-Transport-Security`, `X-Content-Type-Options`, `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`.
- Credentials: no plaintext key, token, webhook secret or provider token in DB columns, logs, job payloads, Inertia props, audit details or emails (automated scanners from M3, M8, M9 run together here).
- Authorization parity: every portal action has the same outcome through the API, CLI and MCP paths (permission parity test from the capability table).
- Egress: SSRF suite (M9) plus the network egress proxy verified from a worker host.
- Admin console (M7): customer sessions rejected, no rule contents in responses, two-person actions.
- Rate limits: management, delivery, evaluation, ingestion, login and invitation endpoints each return `429` with retry guidance at their configured limits.
- External penetration test of the staging environment, scope: portal, API, SDK endpoints, webhooks and OAuth flows, admin console. Findings policy: no open critical or high findings at go; medium findings have an owner and a date.

| Cache keys | After running the seed flows, a Redis key scan asserts every tenant key starts with `tenant:{org}:` and no snapshot cache key lacks environment and projection |

| Telemetry connection | Same scope test as the main connection (M10) |
| Credentials | An Acme SDK key cannot read Globex snapshots, send Globex events, or reach any management route; a Globex management token cannot act on Acme |
| Stale membership | A removed member's session and personal tokens fail immediately |

| L5 Publication under load | Publish latency and outbox age while L1 to L4 run |

**Backup and restore drill.**

1. Preconditions (D08): managed MySQL with point-in-time recovery and encrypted backups; encryption keys stored and recoverable separately from the backups; Redis treated as rebuildable; private object storage (if selected) versioned.
2. Prepare a production-like environment with synthetic tenants, a long-running `bitflag-php` client with a persistent cache per environment, a webhook receiver, and a Slack test workspace.
3. Take the restore point T. Publish several revisions after T so that clients hold `(generation g, revision N + k)`.
4. Simulate the disaster and restore the database to T on a new instance. Record the start time.
5. Put the whole application into maintenance mode, **including delivery**. Restored data can contain credentials, memberships and sessions that were revoked after T; nothing may authenticate against them until step 7.
6. Revoke every portal session and trusted browser (all users sign in again). Sessions are cheap to recreate and impossible to reconcile individually.
7. Run `php artisan ops:replay-recovery-journal --since=T`: re-apply every journal line after T idempotently (revoke credentials and personal tokens, remove memberships and lower roles, revoke invitations, re-suspend organizations, re-create subject deletion tombstones and run the deletions). Accounts whose password or MFA changed after T are flagged "password reset required" and receive an email, because the restored database holds their old secret. Lines that cannot be applied (for example a revocation of a credential created after T, which no longer exists) are reported, not ignored.
8. Run `php artisan bitflag:delivery:bump-generation --all --reason="restore 2026-…"`: for every environment, `generation` becomes `max(current + 1, unix_seconds(now))` and the current pointer's snapshot is re-issued under the new generation (new ETag and checksum envelope, same configuration content), with audit entries (channel `system`) and an internal outbox message. Then flush delivery caches, credential caches and rate-limit state in Redis, warm caches from MySQL, and lift maintenance mode for delivery only.
9. Reconcile: outbox messages after T are lost, and their external effects (webhook deliveries, Slack posts, Datadog events) already happened and cannot be retracted; Stripe reconciliation job repairs billing; SDK keys and tokens created after T no longer exist and must be re-issued (customer communication, using the journal to list affected organizations); telemetry for the gap is marked as a degraded-data window shown in Analytics and on running experiments.
10. Verify: the cached client moves from `(g, N + k)` to `(g', N)` with `g' > g` and serves the restored configuration; a client at `(g', N)` refuses an older generation; a credential revoked after T is rejected; webhook receivers get `revision.published` with `source: recovery` (proposed addition) and can deduplicate by event ID.
11. Lift maintenance mode for management, record the end time, compute recovery time and data loss against the agreed RTO and RPO, and write `docs/operations/drills/{date}-restore.md` with timings, problems and fixes.
12. **Repeat the drill from an older backup** taken before the first drill's restore point, without resetting the clients: the second bump must still produce a generation above the one clients hold.

A second, shorter drill restores only from backups plus the escrowed encryption key on a clean account, to prove that the keys are recoverable.

**Monitoring and alerting.**

| Signal | Source | Alert (threshold agreed under D08) | Runbook |
| --- | --- | --- | --- |
| SDK snapshot availability | External synthetic canary (`ops/canary`: a `bitflag-php` client in a separate network fetching and evaluating every minute for a canary organization) | Failed checks in a row | Delivery outage |
| Publish commit-to-delivery | Canary publishes to a canary environment every 5 minutes and measures when the canary client sees it | Above target | Failed publication delivery |
| Outbox oldest pending age | App metric per message type | Above target | Failed publication delivery |
| Queue wait time | Horizon metrics per queue (`publication`, `default`, `integrations`, `telemetry`, `reports`) | `publication` above seconds-level target; others above their own | Queue or cache outage |
| Failed jobs | Horizon | Rate above baseline | Per job owner |
| Ingest journal lag | M10 metric | Oldest pending batch above target; backpressure active | Telemetry loss |
| 5xx rate and latency | Per route group (portal, api, sdk, admin) | Above error budget burn rate | Bad deploy |
| Delivery `401`/`403`/`429` rates | M10 rollups (aggregate across tenants) | Sudden spikes | Credential compromise, abuse |
| Database | CPU, connections, lock waits, replication lag, storage | Above target | Database |
| Redis | Memory, evictions, connected clients | Evictions on queue connections | Queue or cache outage |
| Scheduler heartbeat | Heartbeat job writes every minute | Missed for 5 minutes | Scheduler |
| Backups | Provider backup status | Any failed backup | Data restore |
| Stripe and email | Webhook verification failures, processing lag; bounce and complaint rates | Above baseline | Provider outage |
| Security signals | Login failure spikes, lockouts, MFA resets, admin console two-person actions | Spikes or any unexpected staff action | Security incident |
| Certificates and domains | Expiry | 21 days before expiry | Certificates |

Logs are structured JSON with `request_id`, tenant IDs and actor type; a log processor redacts known secret patterns and a test asserts that keys and tokens never reach log output. Tooling is D08 (proposal: OpenTelemetry instrumentation with a managed backend, Horizon for queue views).

**No placeholders in production.** A release check (`php artisan release:verify`) fails if: the demo shell or seeders are reachable in production, any egress test allowlist is set, any provider adapter is a fake, `experiments.verdicts_enabled` is on without the recorded D07 sign-off file, debug mode or Telescope-like tooling is enabled, or a required secret is missing.

### 3.3 Actions

| Action / command | Module | Actor and guard | Effect |
| --- | --- | --- | --- |
| `BumpDeliveryGeneration` via `php artisan bitflag:delivery:bump-generation {--environment=*} {--all} {--reason=}` (M5 command, extended here) | Publishing | Operator on a production host; requires `--reason` and an interactive confirmation naming the count of environments | Generation becomes `max(current + 1, unix_seconds(now))`, re-issue current snapshots, audit `environment.generation_bumped` (channel `system`), outbox `internal.delivery.generation_bumped` and `revision.published` with `source: recovery` |

| `php artisan release:verify` | Shared | CI and operator | §3.2 "No placeholders" checks |
| `php artisan retention:report` | Shared | Operator | Summarize `retention_runs` against the matrix |

### 3.4 Routes

| Route | Purpose |
| --- | --- |
| `GET /up` | Laravel liveness (no dependencies) |
| `GET /internal/health/ready/{role}` | Readiness per process role, so one dependency's outage only removes the instances that need it. `web` (portal and management API): main MySQL and Redis. `delivery` (`routes/sdk.php` snapshot and evaluate): main MySQL only, because Redis is an accelerator with a MySQL fallback (M5). `ingest` (`POST /sdk/v1/events`): telemetry MySQL. `worker`: the connections its queues use; scheduler heartbeat age and Horizon status only for the scheduler and Horizon roles. A telemetry outage must never mark `web` or `delivery` instances unready. If roles share instances (D08), the load balancer routes each path family by its own role check. Bound to the internal network or protected by a shared secret header; never exposes tenant data |
| `GET /internal/metrics` | Metrics export if the chosen tooling scrapes (D08); same protection |

No portal or management API routes are added.

### 3.7 Security and tenant isolation

- The canary organization is a normal tenant with its own keys, excluded from billing and from customer-facing counts; it never has staff access to other tenants.
- Operator commands run only on production hosts through the deployment tooling, log the operator identity, and write customer audit entries with channel `system` where tenants are affected.
- Penetration testers get a staging environment with synthetic tenants only; no production data is copied (operations §2).
- Load-test tenants and keys are created by a seeder that refuses production.

## 4. Implementation steps

1. **Coverage inventory.** `tools/mockup-inventory` script and `docs/acceptance/mockup-coverage.md`; mark every artboard; open defects for gaps.
2. **Accessibility automation.** `cypress-axe` helper in `cypress/support/a11y.ts`, calls added to all existing specs; `vitest-axe` for `components/ui`; `tests/js/tokens-contrast.spec.ts`; `eslint-plugin-vuejs-accessibility` in the ESLint config.
3. **Responsive automation.** `cypress/e2e/m12-responsive.cy.ts` iterating key pages and states at 1440, 1280, 1024, 768 and 390 with overflow and primary-action assertions; screenshot artifacts.
4. **Manual accessibility and responsive passes.** Checklists in `docs/acceptance/accessibility.md` and `responsive.md`; fixes in owning modules.
5. **Isolation suite.** `tests/Feature/Isolation/RouteInventoryTest.php`, `IsolationMatrix.php`, `QueryIsolationTest.php`, `JobContextTest.php`, `CacheKeyScanTest.php`, Globex mirror seeder, arch rules.
6. **Security tooling in CI.** Semgrep, CodeQL (TS), gitleaks with custom rules, `tools/scan-bundle`, `composer audit`, `npm audit`, SBOM and license jobs in all four repositories.
7. **Security review.** Threat model, ASVS checklist, header tests, rate-limit verification tests, external penetration test, fixes and retest.
8. **Load testing.** Agree targets (D08), k6 scenarios L1 to L9 in `tests/Load/`, synthetic tenant seeder, runs, bottleneck fixes, report `docs/operations/load-test-{date}.md` stating measured conditions.
9. **Observability.** Instrumentation, structured logs with redaction test, health routes, dashboards and alerts per §3.2, external canary, canary publish job.

## 8. Risks and open questions

- **Targets are missing.** Load, freshness, RPO and RTO targets do not exist yet (D08). M12 cannot finish without them; agreeing them early lets M5 and M10 design toward them.
- **Muted text contrast.** The mockups render secondary text as the text color at 55% opacity on dark surfaces; this may fail 4.5:1 in places. Fixing it may change the Nocturne token mapping.
- **Generation bump and webhooks.** `revision.published` does not have a `recovery` source in R02 payloads; adding it touches the protocol (D03).
- **Restore cannot retract external effects.** Webhooks, Slack posts and Datadog events sent after the restore point stay sent; customers need a documented explanation.
- **Accessibility level is not in the decision register.** Adding it to D01 (or a new item) makes the gate explicit.
- **Mobile expectations** (390 px) are proposed here; frontend doc §7 asks for them to be explicit before acceptance.
- **Penetration test timing** must leave room for fixes and a retest before go.
- **M13 dependencies** (SDKs, adapters, CLI, MCP, website, docs) are part of the release gate and planned in M13; their readiness can block go even when the core is done.
